{{- if not (or .Values.ingress.enabled .Values.httpRoute.enabled) }}

No Ingress or HTTPRoute was created, so nothing routes to kinora from outside the cluster yet.
Either set `ingress.enabled=true` (or `httpRoute.enabled=true`), point your own load balancer at
the {{ include "kinora.web.fullname" . }} Service, or try it locally:

  kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "kinora.web.fullname" . }} 8080:{{ .Values.web.service.port }}

  ...with `--set publicUrl=http://localhost:8080`, since publicUrl must be the URL your browser
  actually uses.
{{- end }}
{{- if hasPrefix "http://" .Values.publicUrl }}

! publicUrl is http://, not https://. Session cookies and the trace viewer's service worker
  both behave differently over plaintext - fine for a port-forward or a local trial, not for a
  real deployment.
{{- end }}
{{- if and .Values.ingress.enabled .Values.httpRoute.enabled }}

! Both ingress.enabled and httpRoute.enabled are set. That is legal - it is how an
  Ingress -> Gateway API migration looks - but it is usually a mistake.
{{- end }}

Send your first run:

  npx @kinora/cli upload --url {{ include "kinora.publicUrl" . }} --token <api-token>

  Sign in, create a project, and copy its API token from the dashboard. Then point your
  Playwright reporter at the same URL.

{{- if not (or .Values.retention.artifactDays .Values.retention.runDays .Values.retention.keepLastRuns) }}

! Retention is off, so this instance keeps every run and every trace forever. Traces are what
  fill the disk. A good starting point, which preserves all your history and trends and only
  drops the trace files behind older runs:

    --set retention.artifactDays=30
{{- end }}
{{- if include "kinora.localStorage.enabled" . }}

Artifacts are on a {{ .Values.storage.local.size }} PersistentVolumeClaim
({{ include "kinora.artifactsClaimName" . }}). It is ReadWriteOnce, which is why the server runs
a single replica - configure `storage.s3` to scale out.
{{- end }}
{{- if include "kinora.s3.enabled" . }}

Artifacts go to s3://{{ .Values.storage.s3.bucket }} at {{ .Values.storage.s3.endpoint }}, so no
PersistentVolume was created for them. Two things about that bucket are invisible until someone
opens a trace, because the viewer's service worker fetches it straight from the browser:

  - it needs CORS allowing GET and the Range header from {{ include "kinora.publicUrl" . }},
    and must expose Content-Range, Content-Length, Accept-Ranges and ETag;
  - its endpoint has to resolve from your users' browsers, not just from inside the cluster.
{{- if not (include "kinora.hasSecret" (dict "ctx" . "key" "S3_ACCESS_KEY_ID" "inline" .Values.storage.s3.accessKeyId)) }}

No static S3 credentials were configured, so the server will use the AWS SDK's default
credential chain. On EKS that means the server's ServiceAccount
({{ include "kinora.server.serviceAccountName" . }}) needs a role:

  server:
    serviceAccount:
      annotations:
        eks.amazonaws.com/role-arn: arn:aws:iam::<account>:role/<role>

Without one, this surfaces as CredentialsProviderError on the first artifact upload - not at
startup, so a green install proves nothing here. Upload a run and check the server logs.
{{- end }}
{{- end }}
{{- if .Values.postgres.enabled }}

The bundled Postgres has no replication, no backups and no connection pooler. For anything you
care about, set `postgres.enabled=false` and point `postgres.host` at a managed database.
Back it up with:

  kubectl -n {{ .Release.Namespace }} exec sts/{{ include "kinora.postgres.fullname" . }} -- \
    pg_dump -U {{ .Values.postgres.username }} {{ .Values.postgres.database }} > kinora-backup.sql
{{- end }}
